# Pi HDMI deployment evidence — 2026-10-08

Target: Raspberry Pi Model B Rev 2 (ARMv6, revision 000d), DietPi/Raspbian Trixie, GStreamer 1.26.2.
Two live cameras: Front Door CLE and Garage CLE, side by side on HDMI-A-1 at 1920×1080.
These findings concern the Linux client and the bridge's VA-API encoder, not the SDK stream selector.

## Failures and fixes

1. Both live RTSP hardware decode probes initially failed with `not-negotiated (-4)`.
   Front Door's `h264parse` caps were byte-stream/AU, 524×720 at 15 fps, level 3,
   profile `constrained-high`. The Pi's `v4l2h264dec` advertised baseline, constrained-baseline,
   main and high, but not constrained-high. A six-second capture re-encoded on the bridge using
   VA-API with `-profile:v main` decoded 45 buffers through the Pi's V4L2 decoder to a fakesink
   and ended successfully. After deploying the explicit Main profile in the resized VA-API preset,
   live Front Door RTSP `ffprobe` reported H.264 Main, 524×720, level 30.
2. The installed client emitted `force-aspect-ratio=true` for `kmssink`; the actual plugin rejected
   this unknown property before playback. Removing it allowed rendering. The plugin itself computes
   the display ratio: Front Door's plane was positioned at 786×1080+87+0 within its 960×1080 cell.
3. Independent processes opening the DRM card separately left only Front Door as DRM master.
   Garage failed with `drmModeSetPlane failed: Permission denied (13)`. Sharing one inherited open
   DRM descriptor fixed ownership, but then independent page-flip waits competed for the CRTC:
   `drmModePageFlip failed: Device or resource busy (16)`. The client now passes the same descriptor
   at fd 3 and uses `skip-vsync=true` for those sinks. Each process updates its own overlay plane
   without consuming shared DRM page-flip events. Decoder and watchdog remain per tile.

## Live result and verification boundary

The final dual-tile service started at 07:44:32 UTC. Both pipelines reached PLAYING at 07:44:36 UTC.
The driver's state showed both planes active on the HDMI CRTC, importing decoded YU12 buffers:

| Camera | Plane | Input dimensions | Render rectangle |
| --- | --- | --- | --- |
| Front Door | 98 | 524×720 | 786×1080+87+0 |
| Garage | 109 | 640×720 | 960×1080+960+0 |

Twelve driver-state samples spaced by 200 ms showed nine framebuffer changes on Front Door and ten
on Garage. This proves both planes were advancing during that sample, not an exact delivered FPS.
The user confirmed both camera images were visible and supplied a screen capture at 03:45:29 EDT;
the capture also exposed console login text in the uncovered left margin. The target HDMI getty was
then masked and the base console cleared, with a root ExecStartPre to repeat the clear on startup.
The user confirmed that the login text was gone and both cameras were still moving afterward.
SSH remains available. This console configuration is specific to this dedicated display installation.

The decoder logged initial timestamp/dequeue warnings during startup. The observed dual-tile run
had no pipeline exit, watchdog error or DRM error after the final sharing/vsync change during the
subsequent check. This short test does not establish long-term stability or support for four streams.
Cold-boot verification after the final console setup remains a separate check.

Local checks: all eight Linux client packages passed `go test -race ./...`; `go vet ./...` passed.
The bridge's 102 tests passed, including the VA-API Main-profile preset assertion.
